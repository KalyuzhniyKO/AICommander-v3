# AICommander 3.0 — техническое задание

[English](PRODUCT_SPEC.en.md)

## Цель
Создать команду AI-разработки для `warehouse_config` и новых программ. Владелец ставит задачи с MacBook, а Zorin OS использует **уже работающие** Hermes (руководитель и делегирование) и OmniRouter (выбор моделей). В новом продукте не дублируем эти сервисы.

## Роли

| Роль | Обязанность | Результат |
|---|---|---|
| Владелец (человек) | Требования, бюджет, согласования | Задача и утверждение |
| Директор (Hermes) | Декомпозиция, подбор ролей, контроль | План, статусы, решение |
| Аналитик | Бизнес-правила, сценарии, критерии приёмки | `requirements.md` |
| Архитектор | API, БД, миграции, риски, rollback | `design.md` |
| Программист | Реальные изменения в отдельной Git-ветке; сложное — Codex CLI | Git diff / commits |
| QA-тестировщик | Запуск pytest/Django checks, exit codes, логи | `qa-report.json` |
| Ревьюер | Независимая проверка diff и доказательств QA | `review.md` |
| Владелец (человек) | Приёмка перед merge и deploy | Одобрение/отказ |

## Маршрутизация

Простые задачи направляются бесплатным/дешёвым моделям через OmniRouter. Средние — подходящим моделям по лимитам и специализации. Сложные или рискованные — Codex CLI, а ChatGPT Web применяется **только вручную**, если нужно экспертное обсуждение. Подписка ChatGPT не предоставляет бесплатную автоматическую работу с OpenAI API.

Этапы: `NEW → TRIAGE → REQUIREMENTS → PLAN → IMPLEMENTATION → QA → REVIEW → WAITING_OWNER → DONE`, с явными состояниями ошибок/ожидания/отклонения. Некоторые роли допускается пропускать по решению директора, но реальные проверки кода — нет.

## Основные требования
- Передавать результаты между ролями в структурированных артефактах и сохранять историю с идентификатором задачи/раунда.
- Ограничивать попытки, время и бюджет.
- Различать предложение модели и фактическое исполнение команды.
- Создавать draft PR после безопасной проверки, не объединять код автоматически.
- Хранить секреты вне Git; запускать код только в изолированных worktree/контейнерах и тестовой БД.
- С MacBook управлять задачами через защищённый интерфейс (VPN/SSH, аутентификация).

## Совместимость Python и macOS (обязательное требование)

Полные правила и критерии приёмки: [Политика совместимости Python и macOS](PYTHON_COMPATIBILITY.md) ([English](PYTHON_COMPATIBILITY.en.md)), [Issue #58](https://github.com/KalyuzhniyKO/AICommander-v3/issues/58).

- В GitHub Actions поддерживать Python 3.14 и тестировать все **заявленные** версии Python на Ubuntu/Windows; при выходе нового стабильного Python выполнять отдельную проверку совместимости с последующим включением в CI.
- На **macOS ARM64** обязательно запускать backend-тесты и Chromium/Playwright UI-тесты. Это не означает, что отдельно проверен Safari или конкретный MacBook Air M4.
- Исправлять несовместимость собственного кода и по возможности зависимостей, подтверждая исправление регрессионными тестами. Не ослаблять CI ради зелёного статуса и не ограничивать Python/пакеты без проверяемого технического обоснования.
- Текущий baseline: **Python 3.11–3.14** (Ubuntu/Windows), **Python 3.14** (macOS ARM64). Python **3.15** (стабильный релиз 09.10.2026) требует отдельной проверки и пока не считается поддерживаемым.
- Верхние границы тестовых пакетов (в частности, `Django<5.3` для QA fixtures) должны иметь обоснование и план пересмотра; нельзя автоматически переносить их на runtime приложение.

## Критерий готовности MVP
Одна безопасная задача для тестовой копии склада проходит путь MacBook → Hermes → роли → изменения файлов → pytest и Django checks → независимый Reviewer → GitHub draft PR → явное решение владельца. Production не затронут.
