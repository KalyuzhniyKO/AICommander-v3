# Подготовка #18: допуск запросов и учёт резервов

**Обновление 27.10.2026:** ledger также подключён к runtime приложения; см. [контроль расходов](RUNTIME_SPENDING.md). Описание offline ниже сохраняет границы исходного standalone-компонента.

[English](BUDGETS.en.md) · [Issue #18](https://github.com/KalyuzhniyKO/AICommander-v3/issues/18)

`backend.app.budgets` — отдельная offline-библиотека для проверяемой политики
лимитов. Она не вызывает модели, не выбирает маршруты, не меняет настройки
Hermes/OmniRoute и не добавляет второй Director. По запросу владельца эта часть
разрабатывается при недоступных сервисах, независимо от живой интеграции.

**В текущем приложении библиотека ещё не подключена.** Она не ограничивает расходы
существующих legacy/v2 endpoints и не превращает `/panel/status` в отчёт стоимости.
Полная #18 остаётся открытой. Нет новой конфигурации `.env`, автоматической
миграции рабочей БД или фонового задания.

## Политика сервера

`Policy` задаётся доверенным оператором, не моделью и не клиентским prompt:

- точные разрешённые пары role/model, без выбора «лучшей» модели и fallback;
- max_requests на один account, входные/выходные лимиты одного запроса и общий
  лимит токенов;
- timeout одного запроса и неизменяемый срок жизни account;
- общий денежный резерв в целых **micro-USD** (1 USD = 1 000 000 micro-USD);
- явное `allow_paid`, по умолчанию false; денежный лимит по умолчанию 0;
- базовая/максимальная пауза после quota.

Цена неизвестна (`tariff=None`) — запрос отклоняется, даже если ID заканчивается
на `/free`. Нулевой объявленный тариф разрешается отдельно от положительного:
положительный требует `allow_paid=true` и достаточного бюджета. Это **не проверка
реальной бесплатности**. Объявленные цены должны быть независимо подтверждены
перед live-подключением. Все опубликованные примеры здесь синтетические.

Стоимость резерва считается отдельно для input/output, с округлением каждой
составляющей вверх до micro-USD. Float, bool, NaN, Infinity, отрицательные величины
и строки вместо чисел отклоняются. Нет курсов валют или догадок о текущих ценах.
Схема: [policy v1](contracts/budget-policy-v1.schema.json).

## Резерв → однократное разрешение → исход

`BudgetLedger(path)` сам ничего не создаёт. Оператор явно вызывает `initialize()`
для отдельного временного/защищённого SQLite-файла. Это собственная схема version 1,
не новая миграция taskflow. Соединения закрываются после каждого действия;
транзакции только короткие SQLite-операции, без HTTP/SDK/исполнения кода.

1. `create_account(id, policy)` сохраняет неизменяемую политику и начало срока.
   Повтор с той же политикой не сбрасывает лимиты/паузу/срок; изменение отклоняется.
2. `reserve(account_id, Request(...))` атомарно проверяет разрешённую роль/модель,
   токены, время, деньги, quota cooldown и число запросов. Успех только резервирует
   ёмкость. Повтор operation ID **не** является новым допуском; другое содержимое
   или account с тем же ID дают конфликт.
3. `claim(operation_id)` ровно один раз переводит reserved в dispatched **до**
   внешнего вызова. Повтор, включая новый процесс/соединение, запрещён. Два
   конкурирующих claim не получают два разрешения. Ledger сам не отправляет HTTP;
   физическое число запросов обязан ограничивать будущий transport.
4. `record(operation_id, Outcome(...))` сохраняет completed/quota/rejected/unknown.
   Повтор идентичного исхода идемпотентен; другой исход отклоняется. Это состояние
   учёта, не доказательство успешного артефакта, кода или QA.

`release_unclaimed()` возвращает только резерв, который ещё не был claim.
Отправленный/dispatched запрос нельзя освободить, даже если клиент отменён или
worker упал. Unknown сохраняет полный резерв, блокирует новые reserve/ещё не выданные claim
в этом account и не может быть незаметно заменён
на дешёвый success. Crash после claim тоже оставляет резерв: takeover/lease retry
нет. Возврат оплаты не обещается; проверенная сверка unknown — будущий отдельный
операторский протокол. Собственная запись claim не доказывает факт HTTP-отправки.

Обе фазы повторно проверяют cooldown/срок/overrun. Пауза, появившаяся после reserve,
блокирует ещё не выданный claim. Время берётся из доверенных часов сервера;
откат часов после сохранённого события блокирует новые действия. Срок проверяется
при admission, а фактический timeout/остановку процесса должен обеспечивать
будущий адаптер. Это не daemon/watchdog и не гарантия жёсткого wall-clock предела.

## Квоты, неизвестный исход и отчёт

429 или структурированный `rate_limit`/`quota_exhausted` создаёт паузу. Она растёт
экспоненциально до max_backoff; более длинный подтверждённый Retry-After **не
сокращается** до этого max. Пауза действует на один account, не на весь провайдер
или API-ключ. Общая защита провайдера остаётся у OmniRoute. Новый account может
выдавать только доверенный код; создание новых account не является способом
обхода provider quota.

Нет автоматического retry, sleep, смены модели или платной эскалации. После паузы
нужен явный новый operation ID и оставшийся лимит. Поздний success другого уже
отправленного запроса не снимает действующий cooldown. HTTP200 сам по себе не
доказывает успешный результат: адаптер должен учитывать структурированную ошибку
SDK/провайдера. 5xx/timeout/обрыв с неопределённым исходом нельзя импортировать как
подтверждённый бесплатный отказ.

Отчёт различает:

- `budget_committed_micro_usd`: резервы плюс переданные суммы там, где они известны;
- `tokens_committed`: зарезервированные или переданные adapter usage;
- `dispatches_claimed`: выданные разрешения, **не** измеренное число HTTP calls;
- `reported_cost_micro_usd`: переданная сумма только при полноте данных по всем
  выданным claim, иначе null;
- `known_cost_subtotal_micro_usd`: известная часть, не общая стоимость;
- оставшиеся лимиты, состояния, паузу и признак overrun.

Usage/cost от адаптера — доверенные входные метаданные, не проверенный invoice.
Отсутствие billing не превращается в ноль даже при объявленном нулевом тарифе.
Превышение заявленных токенов/резерва сохраняется и блокирует новые reserve/claim,
включая уже ожидающие. Для runtime ограничения стоимости нужны также реальные
провайдерские caps; цены за cache/reasoning/другие сборы этой моделью не покрыты.

Основные причины отказа: `pricing_unknown` — нужна проверенная цена;
`paid_approval_required` — нет разрешения на платный маршрут;
`route_not_allowed` — роль/модель не разрешены; `input_limit`, `output_limit`,
`timeout_limit`, `request_limit`, `token_budget`, `money_budget` — исчерпан лимит;
`deadline_exhausted` — запрос не помещается в срок; `provider_cooldown` — пауза;
`usage_overrun` — ранее замечено превышение; `outcome_unknown` — не разрешён
неизвестный исход; `reservation_exists` — это повтор,
не разрешение на новую отправку. Никакие prompt/credentials/raw error body в схему
не входят. Идентификаторы считаются публичными метаданными: нельзя передавать
в них ключи; библиотека не является универсальным распознавателем секретов. Ошибки хранилища не раскрывают SQL/путь/исключение провайдера.

## Воспроизводимый offline-пример

```bash
python -m backend.app.budgets.demo
python -m pytest -q tests/test_budgets.py
```

Команда использует TemporaryDirectory, искусственные часы и ответы 429/unknown,
не сеть. [Фактический вывод](contracts/budget-offline.example.json) сверяется
тестом. [QA](qa-issue-18-offline.json) включает конкурентные reserve/claim,
reopen/replay, денежные границы, overrun, quota и rollback версии SQLite.

Далее: проверенные тарифы/usage и safe error mapping существующего Hermes bridge;
атомарная связь бюджетного reserve/claim с StepOperations (два независимых commit
не считать атомарной операцией); provider caps, роль/модель через OmniRoute,
проверенная сверка billing и отображение настоящего отчёта в панели. Codex CLI и
ручной экспорт ChatGPT Web остаются зависимыми этапами. Без этих проверок нельзя
объявлять free-first routing и контроль реальных расходов готовыми.
